# DSM 7 SPK Implementation (0.2.0)

> **Scope**: `spk/` is the main implementation; `spk-docker-project/` is an experimental variant.
> **Verification status**: Local structure/script/Docker Compose rendering checks pass; **no real DSM device testing**.
> Items marked "unverified" in this document must not be treated as working.

## 1. Goals and Boundaries

Run a headless dsh container on Container Manager in DSM 7.2+; the SPK is responsible for:

- Package Center install/upgrade/uninstall;
- Package start/stop and `status`;
- Locating Docker/Compose and initializing the data directory;
- Extracting the first-boot token URL to a stable file and providing the `token` command;
- Port registration (recognizable in the firewall UI);
- On uninstall, cleaning up only runtime state without deleting user data by default.

The 0.3.0 SPK does **not** install Node/dsh into the DSM system Node; the runtime stays in the container. The later 0.4.0 native package (see `spk-native/`) instead bundles its own Node 24 runtime and is now the preferred approach.

`package.tgz` unpacks to `/var/packages/dshd/target`, so the path is

`scripts/` installs to `/var/packages/dshd/scripts/`.

Notes:

- `arch` lists both `x86_64 armv8`. The package itself contains only scripts/compose and no native binaries; images are
  built/imported separately per arch, so one SPK can cover both machine types; **this does not mean the image is portable across arches**.

  compatibility regressions in older Package Center versions.
- `version="0.2.0"` is a project requirement; the official docs recommend the `feature-build` form (e.g.
  `0.2.0-0001`). Whether DSM 7.2 accepts a plain three-part version is **unverified**.
- `support_center="no"`: no Synology Support Center integration.
- The `category="productivity"` value has not been verified in a real Package Center.

## 3. Privilege Model

`conf/privilege`:

```json
{
  "defaults": { "run-as": "package" },
  "ctrl-script": [
    { "action": "postinst",  "run-as": "root" },
    { "action": "preuninst", "run-as": "root" },
    { "action": "start",     "run-as": "root" },
    { "action": "stop",      "run-as": "root" },
    { "action": "status",    "run-as": "root" }
  ]
}
```

### Why root is needed

Container Manager's Docker socket (usually `/var/run/docker.sock`) is owned by root, and
`docker compose` needs to access it. Options:

| Option | Grant scope | Persistence | Conclusion |
|---|---|---|---|
| `ctrl-script` runs start/stop/status as root | Only the 5 control scripts | Short-lived | **Adopted** |
| Add the package user to the `docker` group | Equivalent to root (can mount the host `/`) | Persistent | Rejected |
| `sudo` for each action | Not guaranteed available in the DSM script environment | — | Unreliable |
| `docker-project` worker | Handed to Container Manager | Persistent worker | Experimental variant |

Trade-off: root control scripts remain a high-privilege surface. To reduce the risk:

- Only `postinst`/`preuninst`/`start`/`stop`/`status` are elevated; all other files in the package
  run as `package`;
- `start-stop-status` does **not source** `config.env`; instead it parses whitelisted `KEY=value`
  keys and validates types/absolute paths, preventing the package user from injecting root
  commands through a writable config;
- The scripts do not execute user-supplied commands and only invoke `docker compose` at fixed
  paths;
- The `docker` group is not granted to the package user.

`postinst` needs root to create the data directory outside the package directory and the
`/usr/local/bin/dshd-token` link; `preuninst` needs root to stop the Compose project and remove that link.

> Unverified: whether DSM 7.2 accepts `postinst`/`preuninst` root entries in `ctrl-script`;
> the official docs list these actions, but real-device behavior is untested.

## 4. Lifecycle

### 4.1 `scripts/start-stop-status`

Arguments passed by DSM: `start`, `stop`, `status`, `prestart`, `prestop`. `prestart`/
`prestop` return 0 immediately.

`start` flow:

1. Read/create `/var/packages/dshd/var/config.env`;
2. Parse and validate the configuration;
3. Locate Docker (candidate order):
   - `$DSHD_DOCKER`
   - `/usr/local/bin/docker`
   - `/usr/bin/docker`
   - `/var/packages/ContainerManager/target/usr/bin/docker`
   - `command -v docker`
4. Verify `docker compose version`; on failure, look for a `docker-compose` executable;
5. Create `$DSHD_DATA_DIR/home` and `$DSHD_WORKSPACE_DIR`; when running as root, chown the top-level
   directories to `DSHD_PUID:DSHD_PGID` (default 1001:1001, non-recursive);
6. If the container is already running: re-extract the latest token from the logs (do not trust a potentially stale token file);
7. Check that the local image exists (`docker image inspect`); if missing, fail, so that Compose does not
   silently pull an unexpected tag;
8. `docker compose up -d --remove-orphans`;
9. Poll the container ID/running state and the logs, waiting for a URL of the form
   `dsh web: https://host/?token=...`;
10. Write `token-url.txt` (0600) and `status` (0600), return 0.

**If the token is missing, return 1; do not fake success.** The container is kept for diagnostics; `status` still shows it as running.

`stop`:

- `docker compose down --remove-orphans` (does not delete bind-mount data);
- Delete `token-url.txt` and `status`, write `state=stopped`;
- If Docker is already unavailable (shutdown phase), clean up only local runtime state and return 0, to avoid blocking shutdown.

`status`: returns 0 if the container is running, otherwise 3 (DSM convention). Returns 3 if Docker is unavailable as well.

### 4.2 `scripts/token`

```bash
sudo /var/packages/dshd/scripts/token
sudo dshd-token        # link that postinst attempts to create
```

Reads `/var/packages/dshd/var/token-url.txt` and prints it to stdout. The file is 0600 root;
non-root users get a hint to use `sudo`. The URL contains a bearer credential and should be treated as a password.

### 4.3 `scripts/installer`

`postinst` → `installer init`:

- Create `var/`;
- On first run, copy `config.env.example` → `config.env`; keep it if it already exists;
- Create the data/workspace directories and set the top-level owner per `DSHD_PUID/PGID`;
- Try `ln -sfn ... /usr/local/bin/dshd-token` (failure does not block installation).

`preuninst`:

1. Best-effort run `start-stop-status stop` (ignore failures when Docker is unavailable or the
   config is corrupt) to ensure no container is left behind after uninstall;
2. Call `installer cleanup`: delete the token/status/temp files and the `/usr/local/bin/dshd-token`
   link pointing at this package;
3. **Keep** `config.env`, the dsh home, and the workspace.

## 5. Configuration and Compose

`config.env` lives at `/var/packages/dshd/var/config.env` and is passed to Compose by
`start-stop-status` via `--env-file`. See the template at
[spk/package/config.env.example](../spk/package/config.env.example).

The data/workspace directories must be absolute paths under `/volume*` or the package var directory, and must not contain `..`.
This prevents a tampered config from making root scripts create directories or chown system paths such as `/etc`; the config
parser itself does not execute a shell either.

Key points of `package/docker-compose.yml`:

```yaml
name: dshd-spk
services:
  dshd:
    image: ${DSHD_IMAGE:-dshd-synology:0.2.0}
    container_name: dshd-spk
    init: true
    restart: unless-stopped
    ports:
      - "127.0.0.1:${DSHD_PORT:-3080}:3080"
    volumes:
      - ${DSHD_DATA_DIR:-/volume1/docker/dshd}/home:/home/dsh
      - ${DSHD_WORKSPACE_DIR:-/volume1/dshd-workspace}:/workspace
    environment:
      DSH_BIND_HOST: ""
      DSH_PUBLIC_URL: ${DSH_PUBLIC_URL:-http://127.0.0.1:3080}
      DSH_TRUSTED_HOST: ${DSH_TRUSTED_HOST:-127.0.0.1}
```

- All defaults are loopback and contain no `example.com`;
- Compose publishes only to `127.0.0.1`; TLS is terminated by the DSM reverse proxy;
- `DSH_BIND_HOST` is left empty; the container entrypoint binds to the bridge IP (dsh rejects `0.0.0.0`);
- `DSH_PUBLIC_URL`/`DSH_TRUSTED_HOST` must match the reverse-proxy domain;
- The data directory is a bind mount and is not deleted on uninstall.

`docker compose config` renders this file in local checks and asserts the image tag, loopback port,
public URL, and absence of `example.com`.

## 6. Port Registration

`conf/resource`:

```json
{
  "port-config": {
    "protocol-file": "port_conf/dshd.sc"
  }
}
```

`package/port_conf/dshd.sc`:

```ini
[dshd_web]
title="DSHD"
desc="DSHD web UI (loopback only; expose it through a reverse proxy)"
port_forward="no"
dst.ports="3080/tcp"
```

The official Port documentation's example places the `.sc` at a target-relative path (e.g.
`port_conf/xxdns.sc`), so the file lives under `package/port_conf/` in `package.tgz`.
`port_forward="no"` means it is not recommended in the router port-forwarding list, but the application should still appear in the firewall UI.

> Unverified: whether the DSM 7.2 firewall/port-forwarding UI correctly reads this `protocol-file` path,
> and how `checkport="yes"` conflict checking behaves for 3080.

## 7. Reverse Proxy / Web Service (candidate, not enabled)

### 7.1 Recommended: manual reverse proxy in DSM Control Panel

Control Panel → Login Portal → Advanced → Reverse Proxy:

- Source `https://<domain>:443`, bound to the DSM certificate;
- Destination `http://127.0.0.1:3080`;
- Enable WebSocket under custom headers;
- `DSH_PUBLIC_URL` / `DSH_TRUSTED_HOST` in `config.env` point to the same domain.

This is the currently recommended path because DSM's built-in nginx is managed by Control Panel and does not depend on WebStation.

### 7.2 Candidate: `webservice` worker

[spk/conf/resource.webservice.example.json](../spk/conf/resource.webservice.example.json)
provides a complete `webservice` resource candidate:

```json
{
  "webservice": {
    "services": [{
      "service": "dshd",
      "display_name": "DSHD",
      "support_alias": true,
      "support_server": false,
      "type": "reverse_proxy",
      "proxy_target": "http://127.0.0.1:3080",
      "proxy_headers": [
        { "name": "Host", "value": "$host" },
        { "name": "Upgrade", "value": "$http_upgrade" },
        { "name": "Connection", "value": "$connection_upgrade" }
      ],
      "proxy_http_version": 1,
      "connect_timeout": 60,
      "read_timeout": 3600,
      "send_timeout": 3600
    }],
    "portals": [{
      "service": "dshd", "name": "DSHD", "type": "alias", "alias": "dshd"
    }],
    "pkg_dir_prepare": []
  }
}
```

Field definitions follow the official Web Service (DSM 7.0+) documentation; `pkg_dir_prepare` is a
required array in that worker, so an empty array is given. **It is not placed in the active `conf/resource`** because:

- The `webservice` worker is provided by WebStation, and the SPK neither declares nor verifies that dependency;
- The alias portal's actual hostname, TLS certificate, and Host header forwarding versus dsh's Host/Origin gate
  have not been confirmed on a real device;
- dsh's token URL must match the public origin, and the address generated by the portal may not match.

Verify on a real device before merging, and ensure `DSH_TRUSTED_HOST` matches the actual access domain.

## 8. Build, Install, Upgrade, Uninstall

### Build

```bash
./spk/build-spk.sh
# dist/dshd-0.2.0.spk
```

The build script will:

- Parse `INFO` and validate the `package`/`version` formats and required keys;
- Check all required files, icon dimensions, JSON, `.sc`, and script syntax;
- Reject `example.com` in `package/` or the default configuration;
- Generate `package.tgz` (members rooted at `package/`) and the SPK root members.

`spk-docker-project/build-spk.sh` generates
`dist/dshd-docker-project-0.2.0.spk`, for experimentation only.

### Before installation

1. DSM 7.2+, with Container Manager installed and started;
2. Image imported: `docker image inspect dshd-synology:0.2.0`;
3. The data/workspace parent directories exist or can be created;
4. If using a reverse proxy, the domain resolves and a certificate is bound.

### Install

Package Center → Manual Install → `dist/dshd-0.2.0.spk`; or:

```bash
sudo synopkg install /volume1/.../dshd-0.2.0.spk
sudo synopkg start dshd
sudo /var/packages/dshd/scripts/token
```

### Upgrade

DSM order (documented): stop old → preupgrade new → preuninst old → postuninst old →
preinst new → postinst new → postupgrade new → start new.

This package has no `preupgrade`/`postupgrade`; `postinst` keeps the existing `config.env`, so an upgrade
does not overwrite user configuration. New config keys fall back to the built-in defaults in `start-stop-status`. The data directory
is unchanged.

> Unverified: whether `preuninst` runs during upgrade while the old target still exists, config retention, and rollback.

### Uninstall

`preuninst` clears only token/status/links and keeps configuration and data. To delete everything:

```bash
sudo rm -rf /volume1/docker/dshd /volume1/dshd-workspace
```

> Unverified: whether DSM automatically deletes `/var/packages/dshd/var` after uninstall (even if it does,
> the data directories remain); the "delete package settings" behavior in Package Center.
